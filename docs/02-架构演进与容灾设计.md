# 02. 架构演进与双引擎并发聚合容灾设计

## 一、 核心设计哲学

商业搜索 API 的正确用法不是"找一个最好的"，而是**把每一个都当资源池**：

- 4 个商业引擎各有**每月自动刷新的免费额度**（Brave 2000 / Tavily 1000 / Exa ~1000 / Firecrawl 500 credits）——这是白送的资产，顺序使用会导致首发引擎额度先耗尽、其余引擎额度闲置；
- 4 个引擎**各有专长**（Exa 神经语义、Firecrawl 正文清洗、Tavily AI 总结、Brave 独立时效索引）——单引擎的覆盖面天然有盲区；
- 免费引擎（DDG/Bing）只是**保险丝**，商业额度全灭才轮到它们。

针对早期"顺序容灾"实现的三个误区，确立 v2.0 架构原则：
> **"场景双引擎并发聚合，额度感知让位；商业全灭才进入免费终极兜底。"**

- 误区一：首选引擎挂了才切换 → 额度集中在首发引擎，其余额度池闲置浪费；
- 误区二：未命中（结果数为 0）算作成功 → 模型拿到空内容；
- 误区三：直接调用单工具（如 `search_exa`）没有防御 → 单点故障直接向模型报错。

> **不做的设计（明确否决）**：不维护"额度感知冷却/让位"。429 无法区分瞬时限流与
> 真实额度耗尽，据此把引擎整月打入冷宫是无依据的猜测——一次瞬时限流就可能误伤
> 还有大量额度的引擎。并发架构下该机制也属多余：真耗尽的引擎会快速返回失败，
> 并发搭档照常出结果，代价只是一次失败请求。商业引擎失败不跨调用记忆，每次
> 调用独立评估。

## 二、 双梯队流转架构图

```
                         [客户端 / LLM 工具调用]
                                    │
                                    ▼
                        ┌───────────────────────┐
                        │    smart_search()     │
                        └───────────┬───────────┘
                                    │
                         【场景识别（mode 显式指定 / auto 关键词路由）】
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
  [技术/学术]                  [深度问答]                    [新闻/时效]
  Exa ∥ Firecrawl             Tavily ∥ Exa                  Brave ∥ Tavily
        │                           │                           │
        └───────────────────────────┼───────────────────────────┘
                                    ▼
  ====================================================================
  【梯队 1：商业引擎双主力并发聚合（Promise.allSettled）】
  ====================================================================
  * 双方成功 → mergeResults 合并去重、交错排序，一次调用产出两家引擎的并集
    （去重键 = 剥离追踪参数后的归一化 URL，内容 query 保留；同一条结果取两家
    更长的标题/正文择优合并，如 Exa 全文 > Brave 短 snippet）
  * 单方失败 → 并发搭档的结果已经足够，不再追加调用（避免过度消耗额度）
  * 双主力全灭 → 按场景顺位依次尝试剩余商业引擎
  * 失败不跨调用记忆：每次调用独立评估，不基于 429 猜测引擎额度状态
                                    │
                                    ▼ (所有商业引擎均尝试且全军覆没)
  ====================================================================
  【梯队 2：免 Key 免费引擎终极兜底防线（永不断联）】
  ====================================================================
  * 步骤 2.1：DuckDuckGo (HTML POST 接口)
    - 4.5 秒极速超时熔断；失败后进入冷却记忆，冷却期内直接跳到 Bing，
      不再反复支付超时等待成本。
            │
            ▼ (超时、被阻断或处于冷却期)
  * 步骤 2.2：最终保底 微软必应 (cn.bing.com)
    - 国内毫秒级直连，解析真实目标落地页。
    - 保障 100% 成功交付结果给模型。
```

## 三、 场景 × 双主力配对依据

配对同时考虑**专长互补**与**额度池大小**（额度横评详见 `05-高品质商业搜索API月度免费额度横评.md`）：

| 场景 | 并发双主力 | 依据 |
| :--- | :--- | :--- |
| auto（默认/最大流量） | Tavily + Brave | 两大额度池（1000+2000）承接高频调用，AI 总结 + 独立索引互补 |
| tech | Exa + Firecrawl | 神经语义找深度资料 + 落地页清洗成 Markdown；Firecrawl 500/月最稀缺，耗尽自动让位 Tavily |
| deep_qa | Tavily + Exa | AI 总结摘要 + 语义召回，问答场景双保险 |
| news_realtime | Brave + Tavily | 独立索引时效性最强 + 结构化摘要 |

## 四、 单工具调用的防呆防护 (Defensive Wrapper)

用户或大模型有时不会调用综合路由 `smart_search`，而是直接点名调用单引擎工具：
`search_exa` / `search_tavily` / `search_brave` / `search_firecrawl`。

### 解决方案：
所有单引擎工具统一走 `executeCommercialSearch(query, count, sceneOrder, preferred)`：
- 被点名引擎作为**并发首发**（`preferred`）；
- 并发搭档自动取场景默认序中的下一个可用引擎，单点调用也享受聚合质量；
- 首发失败或额度耗尽时，由搭档和后续商业引擎顺位补位；
- 只有全部商业引擎均不可用时，才走免费兜底；
- 返回结果顶部自动附带降级演变日志，大模型对故障转移完全透明。
