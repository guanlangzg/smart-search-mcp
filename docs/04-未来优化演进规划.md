# 04. 未来优化演进规划

本项目架构清晰，易于扩展。后续如果需要进一步提升性能和体验，建议从以下四个维度逐步迭代：

---

## 一、 内存/持久化缓存层 (LRU / File Cache)

### 现状：
相同的搜索词在短时间内多次提问时，仍会重复向商业 API 发送请求并消耗月度额度。

### 优化方案：
- 引入轻量级内存缓存（如 `lru-cache` 或原生 `Map` 搭配 TTL 机制）；
- 对相同的 `(query, mode, count)` 组合设置 15~30 分钟过期时间；
- 命中缓存时直接毫秒级返回已有 Markdown 结果。
- **收益**：搜索延迟从 1~3 秒直降至 < 5 毫秒，商业 API 额度节省 30%~50%。

---

## 二、 ~~动态健康熔断器 (Circuit Breaker)~~（已评估否决，2026-10）

> **否决理由**：曾实现过"429 按月度冷却让位"版本后被移除。429 无法区分瞬时限流与
> 真实额度耗尽，据此把引擎长期打入冷宫是无依据猜测，会误伤仍有额度的引擎；
> 且 v2.0 双引擎并发架构下该机制多余——真耗尽的引擎快速返回失败，并发搭档
> 照常出结果，代价只是一次失败请求。网络类熔断仅保留在 DDG 一处（失败是
> 直接观测事实，10 分钟内存冷却免超时等待），不扩展到商业引擎。

---

## 三、 正文深度抓取与清洗 (Readability / Page Fetch)

### 现状：
目前仅返回标题、URL 和官方给出的 200~800 字简短 Snippet。某些深度技术文档或长篇博客，简短 Snippet 不足以让 LLM 完整解决代码报错。

### 优化方案：
- 新增独立工具或主流程可选开关 `fetch_content: true`；
- 使用 `@mozilla/readability` + `jsdom` 或纯正文提取算法对排名前 1~2 位的目标 URL 进行轻量并发抓取；
- 提取正文主体 Markdown，随搜索结果一同呈现；
- **收益**：让大模型在一次工具调用中直接“读完网页”，避免大模型还要二次调用浏览器或 Fetch 工具。

---

## 四、 并发投机执行 (Speculative / Race Execution)

### 优化方案：
- 当商业引擎发起请求后，如果超过 2.5 秒仍未返回响应，自动**在后台并发发起 Bing 快速抓取**；
- 哪一方先成功返回结果，就优先采用哪一方的结果，并安全取消另一方的连接。
- **收益**：彻底消除网络长尾抖动带来的等待感，保障平均响应时间极其平稳。
